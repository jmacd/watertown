# Low-cost correctness findings and release gates

Status: release gates satisfied; production activated 2026-09-12.

Date: 2026-09-08.

Production qualification: 2026-09-12.

## 1. Decision

Watertown is a low-cost system before it is anything else. Cost that grows with
retained history for an unchanged or small incremental workload is a correctness
failure, even when the operation succeeds, stays under a configured limiter, or
uses a bounded number of requests.

The required steady-state invariant is:

```text
cost(operation) <= fixed operation overhead + O(actual change)
```

In particular:

```text
unchanged collection:
    no pond data commit
    no backup open
    no backup write
    no remote ref update

small collection change:
    one proportional local commit
    publish only newly required immutable objects
    one bounded publication-state update

retry:
    no duplicate physical payload
    no incomplete snapshot becomes visible
```

Session reuse is not part of this requirement. Each individual collection
command and its backup activity must be efficient on its own. A reusable session
may later reduce process startup and repeated pond-open cost, especially for
selfmon, but it must not conceal inefficient transaction or backup semantics.

This review blocks release until the gates in Section 10 are satisfied.

## 2. Scope and terminology

This review covers:

- producer command behavior;
- deferred limiter-usage recording;
- automatic post-commit backup;
- physical remote object storage;
- remote maintenance;
- consumer read amplification;
- cost regression testing; and
- production verification for water, septic, and Noyo.

The phrase **current snapshot object set** is used here instead of "closure."
It means the immutable objects needed to reconstruct one pond snapshot:
commit objects, manifests, directory and file metadata, inline values, and
other content-addressed nodes reachable from the snapshot tip.

Successive snapshots intentionally share most of these immutable objects. If a
snapshot needs 800 objects and a collection adds five new objects, the next
snapshot may need 805 objects, of which only five are new. Structural sharing is
expected; physically writing the shared 800 objects again is not.

## 3. What Noyo actually does

One scheduled Noyo tick currently launches three independent commands:

```text
pond run /laketech/data pull
pond run /system/site pull
pond run /system/etc/20-hydrovu collect
```

Their roles differ:

| Command | Source | Expected ordinary behavior |
|---|---|---|
| `/laketech/data pull` | `jmacd/noyo-blue-econ`, prefix `laketech` | Fetch and resolve the Git ref; no pond content change when the ref is unchanged |
| `/system/site pull` | `jmacd/caspar.water`, prefix `config/noyo/site` | Refresh static Noyo site content; no pond content change when the ref is unchanged |
| `/system/etc/20-hydrovu collect` | HydroVu API | Append newly available sensor observations |

The first two are dynamic `git-ingest` nodes. Their `pull` operation updates a
bare Git cache outside the pond's versioned namespace. Recent source refs have
usually been unchanged. Only HydroVu is expected to make an ordinary Noyo pond
content change.

The defect described below is therefore not repeated Noyo source retrieval.
It occurs after or around factory execution, in Watertown transaction
bookkeeping and backup publication.

## 4. Discovery: limiter telemetry can create the write it measures

Backup byte and operation usage is recorded in the control table after a push.
Because post-commit backup cannot write the pond without recursively causing
another commit and push, the samples are queued. At the start of the next write
transaction, Watertown appends the queued samples to:

```text
/sys/limits/usage
```

The implementation intended these rows to "piggyback" on a write that was going
to happen anyway. It emits them before factory execution, however, before the
system knows whether the factory will change any other pond content.

This produces a one-command-delayed feedback chain:

```text
backup push records usage in the control table
    |
    v
next `pond run` starts a write transaction
    |
    v
pending usage is appended to /sys/limits/usage
    |
    v
an otherwise unchanged Git pull now has a pond content change
    |
    v
the commit triggers another automatic backup push
    |
    v
that push queues usage for the next command
```

It is not immediate infinite recursion because emission is deferred. It is
still self-sustaining scheduled activity: backup telemetry causes a commit,
that commit causes backup activity, and that backup activity supplies telemetry
for the next command.

On Noyo this can turn all three commands into commits and pushes even when the
two Git sources are unchanged. The HydroVu command then carries both real sensor
changes and usage generated by the preceding site pull.

### Required correction

Pending limiter usage may be appended to the pond only if the transaction
already contains another real content change. It must not make an otherwise
no-op factory transaction non-empty.

Pending telemetry must remain safely queued when there is no real write. Its
retention, capacity, and any loss must be explicit and observable; telemetry
must not be silently discarded to achieve a no-op.

Telemetry-only commits that suppress post-commit backup would break the feedback
loop but would still violate the stronger low-cost requirement that an unchanged
collection produce no pond data commit. They are not the preferred result.

## 5. Discovery: backup did not track what it had published

Before this investigation, normal backup publication materialized the complete
current snapshot object set and submitted it on every content-changing commit.
It did not maintain an efficient publication frontier describing which
immutable objects the remote had already accepted.

For example:

| Push | Objects required by snapshot | Newly introduced objects | Objects submitted by old code |
|---|---:|---:|---:|
| First | 800 | 800 | 800 |
| Second | 805 | 5 | 805 |
| Third | 810 | 5 | 810 |

The intended cumulative physical object count is 810. The old publication path
submitted 2,415 object rows.

This is a critical protocol failure, not merely a missed optimization.
Watertown already had content hashes, snapshot tips, commit ancestry, and a
Merkle-structured snapshot. A content-addressed backup protocol must use that
information to avoid treating an established remote as empty on every push.

### Why it was originally considered safe

The code treated an identical write under an identical content hash as
idempotent. That would be physically idempotent in a key/value object store
where an existing immutable key is retained or replaced in place.

It is not physically idempotent in Watertown's generic Delta `Store`.
`Store::apply_batch` records each put as another versioned row. The latest
logical value remains correct, but old identical rows remain in active Parquet
files.

Thus the old path was logically idempotent but physically cumulative.

## 6. Discovery: compaction preserved the duplicate rows

Delta compaction reduced the number of Parquet files but did not collapse
historical versions of the same object key. It combined many small files into
fewer larger files containing the same accumulated duplicate rows.

This changed the shape, not the amount, of unnecessary data:

```text
before compaction:
    many small Parquet files containing repeated object rows

after compaction:
    fewer large Parquet files containing the same repeated object rows
```

The existing remote cost test asserted that the number of files remained
bounded. That was insufficient. A small file count appeared healthy while
physical row count and bytes per file continued growing.

Automatic remote compaction was consequently amplified too. It periodically
read approximately 24 MiB and uploaded approximately 19-20 MiB to reorganize
accumulated rows without removing the duplicates.

## 7. Discovery: exact consumer queries still scanned inflated files

The consumer did not issue hundreds of object point queries. It used three
exact object batches and zero point queries:

1. root and manifest objects;
2. objects named by the current manifest; and
3. missing physical payload objects.

Those batches returned only about 36 inline objects during the observed Noyo
pulls. Nevertheless, the object-table stage read approximately:

- 42.78 MiB in one pull;
- 44.20 MiB in a later pull; and
- 50.84 MiB in a subsequent pull.

An exact predicate limits rows returned, not necessarily bytes scanned. Object
keys are random hashes. After compaction, each large Parquet file contained a
broad range of hash values, so file statistics could not reliably exclude it
from an `item_key IN (...)` query. The query scanned large files containing
historical duplicate rows and returned only the requested latest values.

The comparison that revealed the amplification was:

| Measure | Observed Noyo scale |
|---|---:|
| Object-table output from an ordinary producer command | approximately 0.4 MiB |
| Total local writes from an ordinary producer command | approximately 0.8-1.0 MiB |
| Inline objects returned by consumer batches | approximately 36 |
| Consumer object-table bytes read | approximately 43-51 MiB |

The consumer charge therefore represented physical read amplification, not
43-51 MiB of new Noyo observations.

## 8. Combined failure mechanism

The complete mechanism was:

```text
unchanged Git pull begins
    |
    v
pending limiter usage makes the transaction non-empty
    |
    v
pond commits and automatic backup runs
    |
    v
backup submits the complete current snapshot object set
    |
    v
Delta appends new physical versions of old immutable objects
    |
    v
compaction combines but does not deduplicate those rows
    |
    v
later exact consumer batches scan the inflated Parquet files
    |
    v
consumer and maintenance cost grows with prior pushes
```

The three Noyo commands did not create the underlying defects, but their
separate transaction boundaries exposed and multiplied them. Combining the
commands into a reusable session would reduce repetition while leaving the
incorrect semantics in place. It is therefore not the fix.

Water and septic execute fewer scheduled commands, so the defects may be less
visible there. They are not cleared. They must be measured against the same
invariants rather than assumed efficient.

## 9. Required design

### 9.1 No-op collection

Factory execution must be allowed to finish without a data commit when it made
no namespace or series change.

Before an automatic backup is opened, Watertown must compare the current local
content tip with the locally recorded acknowledgement from the last successful
push to that remote. Equal tips mean:

- do not open the remote;
- do not enumerate objects;
- do not update a ref;
- do not charge remote operations or bytes; and
- leave any pending limiter telemetry queued.

The local acknowledgement is a cache of successful publication, not the only
recovery record. If it is missing, normal operation may read fixed-size remote
publication state once and restore it. Periodic integrity audits are explicit
operations and must not be hidden inside every collection.

### 9.2 Incremental snapshot comparison

For a changed local tip, the previous successfully published remote tip is the
baseline. Watertown must compare the two snapshots by their content hashes and
walk only changed Merkle paths.

Objects reachable from an unchanged subtree hash are already supplied by the
previous published snapshot and need no traversal or publication. Normal push
work must not download or decode a cumulative list of all hashes ever
published.

If the recorded remote tip is not a known valid baseline, publication must fail
loudly and require explicit reconciliation. It must not silently fall back to
submitting the complete current snapshot object set.

### 9.3 Physically immutable object storage

Immutable payload objects must not use an append-versioned Delta partition as
their canonical physical representation.

They should live under content-addressed object-store keys and use
create-if-absent semantics:

```text
object key = format/version/hash
object value = exact bytes whose digest is hash
```

Properties required:

- the first successful create establishes immutable bytes;
- an existing key is accepted only after appropriate identity verification;
- a retry cannot create another physical copy;
- reintroducing an object from older history cannot create another copy;
- concurrent publishers cannot establish conflicting bytes under one hash; and
- an object becomes visible before any ref is allowed to name it.

Delta remains suitable for small transactional metadata such as refs and
publication bindings. It is not suitable here as an unconstrained
append-versioned key/value table for immutable payloads.

### 9.4 Bounded publication state

The remote must expose fixed-size current publication state that identifies at
least:

- the published snapshot tip; and
- any publication-record head or format marker needed for recovery.

A publication record may describe the previous record and objects introduced
by one push. Such records permit replay or audit after local state loss without
requiring normal pushes to read all history.

The exact record format remains a design decision. The invariant does not:
routine publication state reads and writes must be bounded independently of
remote age.

### 9.5 Publication ordering

Publication must preserve:

```text
new immutable objects durable
    before
packs or indexes that name those objects
    before
atomic publication of the new snapshot tip
```

A failure before the final state update leaves the old snapshot current and
fully fetchable. A retry may repeat bounded metadata operations, but it must not
duplicate payload bytes.

### 9.6 Explicit capsule reset and cutover

Existing native ponds and remotes will not be migrated in place. The portable
`pondcapsule.4` representation is the format boundary:

1. Freeze the old pond and record its exact source tip.
2. Publish, download, and independently verify a capsule for that tip.
3. Import the capsule through bounded, journaled transactions into a fresh
   new-format pond with a fresh identity.
4. Rebuild a capsule from the staged pond and verify exact logical
   equivalence.
5. Keep all restored automatic factories and remotes persistently suppressed.
6. Attach a fresh new-format remote, publish, and prove pull/recovery.
7. Run explicit activation preflight before enabling automatic dispatch.
8. Retain the old pond and remote during the rollback window.

The cutover does not preserve native commit history or the old pond identity.
Those are retained with the rollback copy. It preserves and verifies current
logical content, ordered series leaves, schemas, timestamps, bounds, and
attributes.

A full legacy inventory remains acceptable for extracting or independently
auditing the old capsule. It is not part of ordinary new-format push or pull.

## 10. Release gates

All gates below are required before this work is release-ready.

| ID | Gate | Required proof |
|---|---|---|
| LC-1 | Unchanged Git pull is a true no-op | `/laketech/data pull` and `/system/site pull` against unchanged refs do not advance the data version or content tip |
| LC-2 | Telemetry does not create work | Pending limiter usage alone creates no pond commit and no backup push |
| LC-3 | No-op skips remote open | Repeated unchanged commands record zero backup-store operations and bytes |
| LC-4 | Publication has a bounded frontier | Normal push reads fixed-size publication state, not an all-history object inventory or cumulative hash list |
| LC-5 | Snapshot comparison is incremental | Objects beneath unchanged Merkle hashes are neither traversed nor submitted |
| LC-6 | Payload writes are physically unique | Retrying or reintroducing a hash leaves exactly one canonical physical payload |
| LC-7 | Publication remains atomic | Every visible ref is completely fetchable across failures at each publication stage |
| LC-8 | Consumer cost is age-independent | The same small change after 1, 100, and 1,000 prior pushes has comparable requests and bytes |
| LC-9 | Maintenance cost is proportional | No-change maintenance rewrites no payload; selected maintenance bytes are proportional to explicitly selected data |
| LC-10 | Capsule reset is verified | Imported logical content reconstructs exactly; resumable staging, corruption, missing objects, and unsafe activation fail loudly |
| LC-11 | Cost tests measure physical work | Tests assert operations, bytes, physical object count, and rows or files scanned, not file count alone |
| LC-12 | All producers are re-evaluated | Water, septic, and Noyo pass the same no-change and small-change measurements |
| LC-13 | Normal-limit production canary succeeds | Producer, consumer, and maintenance metrics remain within measured proportional bounds without a limiter override |
| LC-14 | Documentation matches behavior | Operator and design documentation describe command boundaries, publication state, recovery, and cost invariants accurately |

LC-12 and LC-13 were satisfied on 2026-09-12 by the measurements in Section
14. All four production timers were then enabled, and their immediately
triggered no-override cycle completed successfully.

## 11. Required regression matrix

### 11.1 Collection and telemetry

Run each unchanged Git pull repeatedly with pending limiter samples present and
absent. Assert:

- the Git cache may refresh;
- pond data version and content tip do not change;
- pending samples remain recoverable;
- no post-commit remote dispatcher runs; and
- remote operation and byte counters remain zero.

Run HydroVu with no new points and with a small known point batch. Assert that
only the latter commits and publishes.

### 11.2 Publication age

Create equivalent small changes after remotes with 1, 100, and 1,000 prior
updates. Compare:

- remote opens;
- metadata requests and bytes;
- snapshot nodes traversed;
- payload create attempts;
- new payload bytes;
- publication-state bytes; and
- elapsed maintenance input/output.

The measurements may have fixed variance but must not grow with prior update
count.

### 11.3 Failure and retry

Inject failure:

- before any object create;
- after some object creates;
- after all objects but before pack publication;
- after packs but before ref publication; and
- immediately after ref publication.

For each point, verify that the visible old or new ref is fully fetchable,
retry converges, and canonical physical payload count does not increase for
already-created hashes.

### 11.4 Historical reintroduction

Publish object `A`, move to snapshots that do not reference it, then introduce
`A` again. The final push may perform a bounded existence/create operation, but
must not store a second physical copy or require an all-history hash catalog.

### 11.5 Consumer reads

For identical requested change sets at different remote ages, record:

- objects requested and returned;
- object-store operations;
- bytes read;
- pack reads;
- Delta metadata reads; and
- any fallback queries.

Consumer bytes must track the requested change, not accumulated history.

### 11.6 Format reset

Exercise capsules containing:

- every supported node and series kind;
- enough entries and leaves to require multiple import batches;
- an interruption after a batch commit but before its journal checkpoint;
- an interruption before a batch commit;
- a conflicting capsule or import parameter on resume;
- a missing payload;
- a hash/value mismatch;
- invalid restored remote configuration; and
- invalid restored automatic factory configuration.

Import must resume without duplicating or skipping logical leaves, reproduce
and verify the exact logical snapshot, never modify the downloaded capsule,
and remain inert unless explicit activation preflight succeeds.

## 12. Implementation status

The accepted native-v2 protocol is implemented on this branch:

- commits use `watertown.commit.v2` and name a persistent path-compressed
  identity-map root;
- the local reserved INDEX node stores only that fixed-size root pointer;
- changed transactions materialize changed identity-map paths, changed trees,
  changed series manifests/payloads, and the new commit into a pond-local
  immutable cache;
- `watertown.series.v3` manifests carry a canonical at-most-64-hash append
  frontier, so a new manifest/root and suffix proof are computed from the
  prior manifest plus new leaves rather than by re-reading the complete
  logical series;
- canonical remote payloads use
  `_content/v2/objects/blake3=<hash>` with conditional create;
- authenticated receipts use
  `_content/v2/receipts/blake3=<hash>` and bind hash, length, and provider
  ETag/version when available; semantic kinds remain authenticated by commit
  and publication records because identical bytes may serve multiple roles;
- per-push records use
  `_content/v2/publications/blake3=<hash>`;
- immutable `watertown.series-pack.v4` indexes use
  `_content/v2/packs/blake3=<hash>`;
- an ordinary series append publishes one suffix pack whose descriptors and
  physical spans cover only the new leaf range; that pack links to the prior
  immutable series hash;
- fixed-key per-series locators point to content-addressed segment packs
  without listing the pack prefix, while an optional separate consolidated
  locator lets explicit whole-range maintenance terminate fresh-clone
  traversal without mutating the historical chain; incremental readers ignore
  it and retain suffix-only cost;
- `pond maintain --collapse-versions N` builds verified whole-range packs only
  in local `data/_packs`; `pond backup publish-consolidated NAME` is the
  explicit, metered, limiter-accounted operation that requires the named
  push/both remote to publish the exact local tip, uploads verified objects
  before the pack, and installs the immutable consolidated locator last;
- user `FilePhysicalSeries`/`TablePhysicalSeries` collapse is retired at the
  public TinyFS path API with an actionable append-or-capsule-reset error; only
  the reserved `.pond-node-index` uses the internal collapsed-pointer writer,
  and maintenance reclaims only those excluded obsolete rows rather than
  claiming user-series/blob reclamation;
- `_publication/` is a dedicated Delta table with one active row per
  `(pond_id, ref_name)`, partition replacement, generation/record-head CAS,
  a checkpoint after every successful advance, and zero-duration removed-file
  and log retention so cold-open metadata does not grow with age;
- producer and consumer acknowledgements are structured and keyed by remote
  URL, pond id, and ref;
- equal acknowledged tips return before storage preparation, limiter binding,
  or remote open;
- consumers with a known tip walk only newer publication records and the
  corresponding series suffix segments; destination planning point-loads only
  changed manifest records and parent paths from its persistent local map, and
  a changed series compares its prior stored `SeriesManifest` frontier/count
  with the authenticated suffix base instead of folding the destination table
  or hashing retained leaves; an initial clone explicitly traverses the
  requested manifest map, snapshot, and only each current series' linked
  segment chain; and
- the full-fold cross-check is an explicit `POND_VERIFY_FOLD` diagnostic in
  every build, not an implicit debug-mode cost hidden from local-work tests.

Small payloads use object-store `PutMode::Create` directly. Large streamed
payloads are hash-verified in a unique `_content/v2/fallback/uploads/` staging
key and promoted with atomic `copy_if_not_exists`, then the staging key is
deleted; this is the object-store 0.12 conditional-create equivalent for the
multipart path, which does not expose `PutMode`. Watertown's S3-compatible
store registration enables object-store's multipart conditional-copy mode by
default; an explicit `aws_copy_if_not_exists` storage option may override it
for providers that require a custom conditional-copy header.

The rejected cumulative object index, ref sidecar, Delta object/commit
publication path, full commit-index scan, object-partition preload, and
`pond backup repair-objects` surface have been removed from ordinary
publication.

Focused tests cover conditional-create retry and historical reintroduction,
receipt-less interrupted creates, malformed receipts, conflicting bytes,
failure injection at every publication stage, visible-state fetchability,
CAS conflicts and ref isolation, changed-path publication, structured
acknowledgements, capsule build/import, one-leaf series append cost after 1,
100, and 1,000 prior leaves, incremental suffix-only materialization, fresh
multi-segment clone, rename/move, missing or malformed segment failure,
publication retry, explicit consolidated-pack success/retry/identity/state and
missing/corrupt local input failures, failure after pack durability but before
locator installation, fresh clone through one consolidated pack, an unrelated
file change beside an unchanged 1,000-leaf series, one-leaf local apply cost
after 1/100/1,000 retained leaves with zero retained leaf hashes scanned, and
equal generic remote consumer cost after 1, 100, and 1,000 prior updates.
Live Azure producer, consumer, acknowledgement, limiter, and activation
qualification completed on 2026-09-12 as recorded in Section 14. The
consolidated-pack and local-planning tests still use local/in-memory backends
and do not independently qualify live S3 behavior.

## 13. Why the earlier efficiency evaluation was insufficient

The prior evaluation correctly identified severe local amplification in
selfmon, but incorrectly described water, septic, and Noyo as efficient.

It emphasized:

- process and pond-open counts;
- local userspace and block I/O;
- successful completion under configured limiters;
- bounded request shape; and
- bounded Parquet file count.

It did not establish:

- which source commands caused real content changes;
- whether bookkeeping created otherwise unnecessary commits;
- why each automatic backup was triggered;
- newly introduced objects versus objects resubmitted;
- physical rows versus unique live hashes;
- bytes scanned per object returned; or
- bytes rewritten by remote compaction.

"Stable all day" established operational stability, not proportional cost.
"Zero point queries" established a better query shape, not bounded physical
bytes. "Below the burst limit" established policy compliance, not efficiency.

Future efficiency reviews must start from source-level logical change and
account for every resulting commit, push, physical byte, consumer read, and
maintenance rewrite.

## 16. Accepted native-format reset and publication design

Accepted on 2026-09-08 after the handoff review.

Existing ponds and remotes do not require in-place native-format
compatibility. Watertown will use the portable `pondcapsule.4` recovery path
as the deliberate format boundary:

1. Freeze the old pond.
2. Publish, download, and independently verify its capsule.
3. Import into a fresh pond using the new native format.
4. Rebuild a capsule from the staged pond and verify logical equivalence.
5. Attach a fresh remote and publish the new format.
6. Prove pull and recovery from that remote before deployment switches.
7. Retain the old pond and remote through the rollback window.

Capsule import currently remains experimental because bounded resume and
active-remote preflight are incomplete. Those are release gates for this
cutover. A capsule preserves and verifies live logical content; it intentionally
creates a fresh pond identity and does not preserve native commit history.

### 16.1 Remote storage boundary

Delta Lake remains the transactional visibility and concurrency boundary.
Moving immutable payloads out of Delta rows does not mean abandoning Delta
transactions.

The accepted split is:

- content-addressed payloads live under raw object-store keys and use
  create-if-absent semantics;
- immutable publication records describe one push and are written only after
  every payload they name is durable;
- a small dedicated Delta publication table holds the active row for
  `(pond_id, ref)`;
- the active row identifies the native format, snapshot tip, and publication
  record head; and
- replacing that row is the final atomic operation that makes a snapshot
  visible.

Payload retries cannot create another canonical copy. A failure before the
Delta publication commit leaves only unreachable immutable objects. Every ref
visible through the Delta table must name a complete, fetchable snapshot.

Multipart payload creation uses unique staging keys because the object-store
multipart API has no create-only mode. Normal completion deletes the staging
key on every success and handled error path. A process crash can still leave a
staging object, so `pond backup cleanup-uploads <name>` performs an explicit,
metered, age-gated sweep of that staging prefix. It never scans or deletes the
canonical payload namespace.

The active publication table must remain physically bounded. Advancing a ref
replaces its one live row rather than accumulating append-versioned ref rows.
Normal opens may read a checkpoint and bounded tail, but must not replay
history proportional to remote age. LC-8 and LC-9 must verify this against the
real production backend.

The initial key layout is:

```text
_content/v2/objects/blake3=<64 lowercase hex>
_content/v2/receipts/blake3=<64 lowercase hex>
_content/v2/publications/blake3=<64 lowercase hex>
_content/v2/packs/...
_publication/                    dedicated Delta table
```

The object value is exactly the bytes whose BLAKE3 digest appears in its key.
`PutMode::Create` is required. On `AlreadyExists`:

- a valid immutable receipt permits a size/identity metadata check without
  retransferring payload bytes;
- an absent receipt means a prior create may have been interrupted, so the
  existing object is read and hashed once before its receipt is created; and
- any mismatch fails loudly as corruption or a conflicting publisher.

A receipt records the object hash, byte length, and the provider ETag/version
returned by the successful create or verification. Native object kinds are
authenticated by commit and publication records rather than payload identity,
so one immutable payload can safely serve multiple semantic roles.
Receipts are themselves canonically encoded, content-addressed immutable
objects. They optimize repeated identity checks; they do not replace explicit
integrity audits.

This protocol assumes the configured S3-compatible or Azure backend provides
strong read-after-write visibility for successful creates and supports atomic
conditional create. Backend qualification tests must prove both assumptions.
Unsupported semantics are a configuration error.

The dedicated publication table contains one live row per `(pond_id, ref)`:

```text
pond_id
ref_name
format
snapshot_tip
manifest_root
publication_record
generation
updated_at
```

The table is physically partitioned so replacing one ref cannot rewrite
unrelated ponds or refs. An advance uses Delta optimistic concurrency and a
compare-and-swap predicate over the prior generation and record head. A
concurrent update, unknown baseline, or non-ancestor tip fails; it never
silently overwrites another publisher.

### 16.2 Incremental snapshot representation

The existing flat node manifest is not the steady-state transfer protocol. It
is rewritten in full and therefore remains proportional to pond size even
after payload rows move out of Delta.

The new native format uses a persistent, path-compressed Merkle map keyed by
`blake3(node_id)`. Commits identify its root. Comparing the acknowledged root
with the new root reads and publishes only changed Merkle paths. Changed leaves
identify the tree, series, and payload objects newly required by the snapshot.
Unchanged subtree hashes prune both traversal and publication.

No cumulative all-object index or complete commit index is read by ordinary
push or pull. A consumer with a known publication record walks only records
since its acknowledged head. The trusted generation delta fixes that read
count before traversal and requires the exact acknowledged record at the
boundary. A tip-only recovery walk is bounded by the active generation. An
initial clone may read the complete requested snapshot.

The destination side is bounded too. An ordinary incremental mirror or graft
reads its fixed local manifest-root cursor, point-loads only changed records
and required parent paths, and applies the publication delta to that map. A
missing/stale cursor is recovered by one bounded latest-row query against the
reserved index, not by opening all index versions. A changed series loads the
prior `watertown.series.v3` object named by its manifest record and compares
its stored count/root/frontier with the authenticated suffix parent. It does not
call the complete-table target fold or reconstruct a frontier from every
retained leaf. Missing or mismatched persistent state fails loudly and
requires an explicit full rebuild.

Logical series use the same bounded rule. `watertown.series.v3` stores the
current leaf root plus its compact append frontier. Each ordinary append emits
one `watertown.series-pack.v4` suffix segment linked to the prior immutable
series hash. Incremental consumers stop the chain at their authenticated local
prefix; fresh consumers walk only that series chain and recompute the latest
complete root from all segment descriptors. A fixed-key consolidated locator
may instead select an explicitly maintained whole-range pack for a fresh
clone. Local maintenance never uploads it: the operator must run
`pond backup publish-consolidated NAME`, which verifies the exact current
remote publication and local pack/object bytes under the attachment limiter,
then publishes objects, pack, and locator in that order. Incremental readers
continue through ordinary append locators. Neither path lists all packs or
rewrites a cumulative descriptor list. A `pond://` source likewise derives
its synthetic publication records only from immutable commit
`introduced_packs`; mutable maintenance/consolidated packs remain discoverable
through their fixed-key locator and never change publication identity at an
unchanged tip.

One immutable publication record contains:

```text
format
pond_id
ref_name
snapshot_tip
manifest_root
parent_publication_record
introduced_objects[]
introduced_packs[]
manifest_changes[]
```

Its lists contain only objects introduced by that push. The record is written
after every named object and pack is durable. The final Delta ref transaction
then names the record. A consumer that has `parent_publication_record` reads
only later records; it does not fetch a cumulative catalog.
`manifest_changes` carries canonical before/after records for the nodes changed
by that push, including deletes. This lets an acknowledged consumer update its
identity view without traversing the complete manifest map.

Every publication generation advances to a distinct commit snapshot. Repeating
the same snapshot is a no-op and does not create a generation; explicit
consolidated-pack publication updates only content-addressed pack locators.
Consequently, record-to-commit binding is strictly progressive, and two
generations may not consume the same commit position.

### 16.3 Local acknowledgement and no-op behavior

Each remote/ref has structured local acknowledgement state keyed by
`(remote URL, pond_id, ref name)` and containing at least the native format,
snapshot tip, manifest root, publication-record head, and generation. When its tip
matches the current local content tip, push returns before:

- storage credentials are prepared;
- limiters are bound;
- the remote is opened; or
- any remote request or byte is recorded.

After local control-state loss, one fixed-size remote publication-state read
may restore this cache. An unknown or non-ancestor baseline fails loudly and
requires explicit reconciliation.

If the remote advanced after its visibility CAS but before the producer
acknowledgement was persisted, retry authenticates the bounded publication
record chain back to the exact acknowledged record (pond, ref, record, roots,
and generation). Every recovered record is checked independently against the
exact local parent-publication-to-record commit interval, including object and
pack inventories and net manifest changes; aggregating several records before
comparison is not sufficient. Named immutable objects and packs must still be
present. The authenticated remote tip then becomes the incremental baseline. Thus an
acknowledged A, remotely visible B, and local C publishes only B-to-C. A remote
record chain that does not descend from A, or a remote tip outside local
ancestry, is rejected rather than triggering a full inventory walk.

When no producer acknowledgement exists, an existing remote row is not trusted
as a baseline merely because its tip commit exists locally. Recovery walks the
record chain under a bound derived from local commit ancestry, requires the
record count to equal the active generation, authenticates every non-genesis
record against its exact local commit interval, and authenticates genesis as a
complete snapshot (including complete series packs). Missing, forged, or
misallocated inventory fails closed.

Pending limiter telemetry is held in control state until commit has established
that the factory already produced another real data change. It may accompany
that commit, but cannot make a no-op transaction non-empty.

The implementation resolves the authoritative current tip from the
pond-resident commit log, caches raw control settings when a pond opens,
defers limiter emission until another pending data operation exists, and skips
acknowledged pushes before storage preparation or limiter binding.
Acknowledgements now contain format, tip, manifest root, publication record,
and generation. Acknowledgement updates use a dedicated process lock, refresh
the authoritative setting while holding it, reject stale generations and
conflicting equal generations, and only permit rollback after an explicit
clear. After control loss, authenticated remote history can restore that state;
an unknown or non-ancestor baseline fails instead of falling back to a full
publication.

Consumer retry closes both the simple and advanced apply/ack crash windows.
The fetched publication window is bound to the exact acknowledged
pond/ref/record/roots/generation lineage. The destination's authoritative
reserved manifest pointer and root record are compared against both roots of
published commits in that window. If A is acknowledged, B was durably applied
without its acknowledgement, and the remote is now at C, retry repairs the
frontier to B and applies only B-to-C in the same invocation. Matching only one
root or an untrusted cache is insufficient. Authenticated zero-net
publications can advance the recovered frontier without rewriting pond data,
while grafts update their replicated source-tip pin atomically.

An exact-identity pull no-op still authenticates the immutable head record and
tip commit. It then performs one bounded authoritative latest-row query for
the destination's reserved manifest index and verifies the root manifest
record; the best-effort cursor is never sufficient for correctness-sensitive
no-op authentication. Grafts apply the same rule to the foreign pond
partition and additionally verify the mount target and pin. If a graft pin is
ahead of its structured acknowledgement, one graph is fetched from the exact
selected active row, authenticated back to the acknowledgement, narrowed
safely to the pin, and then applied. If the acknowledgement was explicitly
cleared, the pin boundary's immutable publication record, commit, and roots
must be reconstructed within the active generation bound before use. This
remains fixed-cost at the destination and bounded by the authenticated remote
window.

Inline publication objects carry their typed `ContentObjectKind` from the fold
site. Raw payload bytes are never classified by magic-prefix sniffing, so a
file beginning with a Watertown wire-format prefix retains a `RawBlob`
receipt across deletion and reintroduction.

### 16.4 Disposition of the experimental diff

Retain:

- physical-row and byte diagnostics;
- authenticated legacy object validation useful to capsule extraction;
- failure-injection scenarios around payload and ref publication; and
- tests that measure duplicate physical storage and age-dependent work.

Do not retain as steady-state protocol:

- the cumulative published-object index;
- its ref sidecar binding;
- Delta object-row filtering based on that index;
- full remote commit-index scans; or
- `repair-objects` partition collapse as a publication prerequisite.

Physical row-count diagnostics remain available at the generic Store layer for
legacy audit work. Partition collapse and its operator command are not part of
the native-v2 publication surface.
